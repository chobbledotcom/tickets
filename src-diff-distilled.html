01 · Distillation rule

Business identity beats syntax.

A parser can say that a declaration appeared in a new file; it cannot say whether that declaration is merely the old Square monolith cut into pieces. This report compares purpose, callers, data touched, and outcomes. A method appears under “genuinely new” only when origin/main has no method doing that job.

Included

New durable refund authority, exact claims, provider permits, closed evidence rules, owner recovery, blind indexed references, and bounded admission.

Updated

An old route or provider method whose name may have changed but whose job remains recognizable—and whose actual decisions or failure behavior changed.

Suppressed

Imports, comments, formatting, helper relocation, route/file splits, Square/refund-ledger decomposition, and aliases/renames with no independent behavior.

No fake precision: this is a reviewed mechanism inventory, not a count of every local arrow function. Small constructors, render callbacks, mapping helpers, schema expressions, and test seams are represented by the public or domain method they support.

02 · Genuinely new methods

New jobs that did not exist on main.

One path, not a compatibility stack: the inventory contains one durable provider-refund engine and one send transition. The old refund sender, refund-local provider-discovery fallback, read-through admission helper, and runtime reader for provider_refunded_at are deleted or absent. Provider adapters require the permit minted by this path. The still-temporary checkout selector is exactly confined to classify.ts, webhooks.ts, and its declaration in payments.ts; an architecture test rejects it from admin refunds, the shared engine, or adapters. Its later replacement is an all-at-once cutover, never a legacy dual or read-through path.

06 · Boundaries that affect interpretation

“Private” and “legacy” need precise wording.

One real engine in production and tests: an architecture inventory pins production and test entry points to requestProviderRefund/requestProviderRefunds, then separately confines the permit mint, lower send methods, and provider API clients. Tests inject provider behavior at reviewed boundaries; they do not exercise a parallel refund implementation.
A route alone is not recovery: lifecycle declarations name the clearer, required choice, and owner route for every blocking state. Static checks prove the exports and route registrations; rendered route/template journeys prove the matching usable control exists for the owner, survives merge or listing deletion, and is absent for a manager who cannot perform it.
Booking-error proof: the changed payment-session path does not turn an unexpected booking exception into success or quietly continue. Primary-state recovery either finishes the exact committed booking, enters protected refund recovery only when rollback is proved, or rethrows the original error. recovery.test.ts, recovery-decision.test.ts, and the webhook post-commit recovery suite exercise all three outcomes. Placeholder creation separately commits the attendee, indexed claimed anchor, and conservative terminal session result together. A simulated post-commit reply loss rethrows on the first request, then replays one attendee with zero new creates and zero provider sends.
No broad decryption: whole-listing and maintenance questions use blind indexes and plain state mirrors. Refund All opens one selected attendee; protected-orphan and canonical-refund queues keyset-page twenty summaries. A live request never decrypts a population to find or repair old payment IDs.
Provider-credential caveat: provider credentials are settings encrypted with DB_ENCRYPTION_KEY. A database-plus-environment-key holder may decrypt them and query provider-held data even though new raw references in this database use the owner public key.
v1-key caveat: “owner-key protected” describes the ciphertext, not a role by itself. Modern password-wrapped owner keys keep new references and attendee PII beyond a database-plus-environment-key holder. Dormant v1 owner-key rows retain the older limitation until the existing upgrade ceremony runs.
Old reference caveat: historical plaintext, DB-key, unindexed, or provider-untagged values can remain stored, but current refund authority does not decode, discover, or provider-map them. Blank-index or unqualified evidence refuses before provider I/O. Only the future bounded, owner-authenticated and owner-authorized M11 migration may qualify them, with verified canonical writes before source redaction. Unqualified values render as inert text; the deleted ambient dashboard helper must not return as a guessed provider link.
Atomic-cutover caveat: this report does not claim that every legacy payment field or the whole checkout/session entry has disappeared. Today the ambient current/last selector is exactly allowlisted to features/api/payment-processing/classify.ts, features/api/webhooks.ts, and its declaration in shared/payments.ts; it cannot enter refund administration, the shared engine, or adapters. The later M6–M11 replacement must activate its writers, readers, jobs, completion, delivery, and M11 migration in the same change that deletes getPaymentProviderForExistingPayments and every runtime payment-ownership caller. There is no permitted dual-run or read-through window. Configuration-only credential enumeration may remain under an honest name; no second observer, sender, fallback, bridge, or old-record branch may coexist.
