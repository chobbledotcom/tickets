01 · What changed

From yes/no guesses to one traceable process.

The old flow mainly asked “is it refunded?” and “did the refund work?”. The new flow keeps the evidence, decision, provider action, and accounting result separate—because each can succeed while another is still unknown.

!

This does not promise that every refund succeeds. It promises something more useful: uncertainty cannot masquerade as failure, success, or a safe retry. If the system cannot prove what happened, it parks the work and preserves why.

Before

Call first, infer afterward

  • Choose one globally configured provider.
  • Reduce provider reads and refund calls to true/false or null.
  • Record accounting only when the whole attendee looked successful.
  • Let refresh, single refund, and bulk refund make similar decisions separately.
  • Use prose history and provider rejection to infer whether work already happened.
Now

Claim, observe, admit, then act

  • Carry the exact provider identity with every new charge.
  • Validate captured money, returned money, currency, statuses, and identities.
  • Refuse incomplete history, then claim the exact admitted rows before provider I/O and keep the claim through accounting.
  • Require a durable dispatch permit immediately before a provider send.
  • Keep exact review cases and confirmation identities separate from human-readable prose.

02 · End-to-end money journey

Ten gates between a click and a completed refund.

The crucial ordering is visible here: completeness is proved for the selected attendees, the admitted row set is claimed, existing safety work across the whole submitted command is checked, and every reference in that command becomes ready before any provider send. A single attendee is simply an array of one, so single and bulk refunds cannot drift apart.

  1. Choose one page

    Check the listing’s complete refundable set for review, books-behind, and blank-index-row blockers without PII, then load at most five real ticket holders with stored charge work.

    Output: bounded attendee revisions ready for the completeness check.

  2. Prove the history is complete

    Load only the chosen attendees. A blank-index historical row, or a current PII payment with no indexed row, returns one typed legacy_unindexed refusal instead of a partial charge list.

    No global scan: unrelated attendees are never selected or decrypted.

  3. Claim the snapshot

    In one transaction, recheck attendee revisions, every reference-bearing row, and every indexed representation of the same charge. A newly appeared blank-index row makes the snapshot changed.

    Changed, incomplete, or already held → stop all.

  4. Admit the action

    An exhaustive action table checks every selected candidate and prices that exact page. Refund All has already refused if the complete refundable set has review, unrecorded money, or blank-index processed history; finished attendees outside that set do not block unrelated work.

    Too much work or one blocked person → zero sends for this page.

  5. Read every provider

    Tagged charges go to their named provider. Indexed, untagged legacy charges are tried at all credentialed providers.

    Missing, unavailable, invalid, or ambiguous → send nothing.

  6. Bind identity & retry rule

    While the claim is held, store the proven provider and whether a repeated request is keyed or keyless.

    Output: stable charge identity + retry capability.

  7. Judge the money

    Shared rules decide: already returned, in flight, owner conflict, or safe to send.

    Only “ready” can request a dispatch permit.

  8. Arm, then send

    Before the durable arm, the request proves and protects the exact provider-send and recovery allowance. The database then moves every holder from ready to send_armed and issues the only permit accepted by provider code.

    Crash boundary: no late budget refusal can strand a definitely-unsent keyless arm; a possibly sent command stays visible.

  9. Record exact money

    Mark each returned charge across all indexed holders, then ask the existing ledger which named groups it can reverse and park every unclear result.

    Output: recorded / review / unrecorded sets for each charge.

  10. Settle each row

    Release rows whose answer is known. Keep claims where money may still move; preserve review cases and books-behind markers.

    Output: durable truth for the next request.

Complete safety, bounded execution

Refund All asks a PII-free SQL summary whether any review, books-behind state, or unindexed processed-payment row blocks the complete refundable set. Only after that passes does it decrypt and execute one page of at most five people; a fully finished attendee cannot block another person’s refund.

Calls are priced, not guessed

Before money moves, the selected page must afford every provider retry, discovery read, recovery read, bounded bulk database operation, rollback, settlement, and route tail. Every non-empty plan reserves the returned-money write before discovery, and the exact send tail is held aside before a durable dispatch arm.

Parallel network, bounded books

Provider calls overlap five at a time. After every wave finishes, the selected page shares one returned-marker write and one ledger call; another submission takes the next page.

Worst result wins

errored → failed → withheld → pending → refunded. A good reference never hides a bad one beside it.

T

Refund and refresh cannot borrow each other’s cost model. Exhaustive action tables price each checkpoint: refund includes the possible send and recovery read, while refresh includes provider observation and its complete confirmation-and-ledger tail but never dispatch arming. Both refuse before taking an unaffordable claim, and a claim admission gate cannot exist without its paired refusal result.

1

Saving an old attendee migrates only the payment ID still in that attendee’s PII. The PII update and its deterministic indexed anchor are one atomic batch. Distinct old balance, merge, or session rows whose index is blank remain a typed refusal for later bounded migration; the refund path never decrypts a population to repair them.

The three merge-risk checks

Errors

Trusted checkout failures stay loud

Only an explicit provider absence or documented visitor mistake becomes an ordinary refusal. Network failures, malformed successful responses, and internal application errors stop before reservation or booking; unknown errors keep their original identity.

Scale

Population questions never decrypt a population

Whole-listing checks use indexed SQL facts. Refund All decrypts at most five selected attendee blobs, and the privacy recovery queue keyset-pages IDs in groups of twenty. Old payments may remain less capable rather than trigger a global scan.

Privacy

The DB key cannot open new raw references

New provider references and attendee PII use the owner’s public key; the database key supplies only a blind HMAC index. Plain columns contain state words and counts, while retained diagnostics accept finite reasons instead of provider bodies, identifiers, or buyer details.

05 · Claims, rows, races, and books

The database becomes the referee between requests.

Provider idempotency alone is not enough—especially for SumUp. The branch adds an all-or-none claim around the exact admitted row set, gives it a command id and explicit phase, and keeps it from before the first provider read until after the ledger result is recorded. Any extra reference-bearing row, indexed or not, invalidates that admission.

grant

No claim exists. This run may hold the row.

held

A fresh run owns it. Send nothing.

resume

A stale claim belongs to this same attendee set. Re-read all evidence.

foreign

Stale work belongs to another owner/scope. Send nothing.

5m

The lease never falls below five minutes. It is the larger of the reservation cleanup setting and one request-lifetime floor. Turning cleanup down cannot make a still-running worker look dead.

1×

Only local state writes queue. Every dispatch-arm and returned-money marker waits for the previous local write to finish; a failed write does not jam later work. Provider requests still overlap within a five-at-once concurrency window; the separate admission budget limits their total physical calls.

Owner means owner

Single refund, Refund All, and review acknowledgement are owner-only at both link and route. Managers cannot view, submit, or replay a refund or an owner-review acknowledgement. Refresh remains a non-sending recovery action for authenticated staff.

Acknowledgement is a receipt

It timestamps the exact case set the owner saw. It does not clear the reason, lift the safety hold, contact a provider, move money, or invent an accounting correction.

Refresh is the repair entrance

Refresh takes the same exact claim but is explicitly allowed to reconcile existing work without sending. A refund is rejected at claim time while unresolved review or unrecorded money exists.

Deleted listing, live work

A review route can still open and log against the attendee when its old listing is gone. The repair target does not become a dead link just because surrounding booking data was removed.

Reachable after merge

The durable row—not old contact PII—shows Refresh

A merge may move books-behind payment rows onto a free attendee whose legacy payment_id is blank. Payment Details still renders the real Refresh form because an indexed payment row exists. The visitor journey merges that exact state, refreshes it without another Stripe send, records Money, and then deletes the attendee.

07 · Honest Part A boundary

What this branch deliberately parks instead of guessing.

Shared indexed representations

Old attendee payments were never shared. If current row operations nevertheless leave several indexed rows representing one charge, Part A claims every holder and parks the charge; it does not invent an allocation across people.

Ambiguous legacy providers

Two validating providers, an incomplete search, or no validation receives no automatic provider choice. Repair and re-attestation are later work.

Keyless uncertainty

A stale SumUp claim stays observe-only until fresh evidence settles it. Even a rejected SumUp request is reread once, because the refusal cannot rule out a refund made elsewhere; an unreadable confirmation stays uncertain. Retaining the row is intentional because it may be the only sign money moved.

Old unindexed payments

They deliberately block that attendee’s refund and refresh, and an unindexed row anywhere in Refund All’s refundable set blocks every send. Saving can anchor the one current PII payment; distinct historical rows wait for a later bounded migration. No request decrypts every attendee.

Historical completion markers

An old untagged “refunded” marker is not treated as provider proof. It stays parked for later repair or audited re-attestation instead of silently reversing the books.

Callback claim scope

Admin single, bulk, and refresh now share the exact claim. Payment callback refunds still lack that same callback-scope claim; finalization does stand down when an admin claim is live.

Acknowledgement is not repair

It cannot allocate a shared charge, correct missing books, or settle provider uncertainty. It records owner awareness while the exact typed case remains the safety authority.

Some owner choices are not built yet

A returned underfunded deposit remains unrecorded with partially_returned_obligation. Refresh cannot invent the missing stable obligation or decide what more is owed; allocation, rejection, and historical-marker attestation need the later revision-fenced owner-choice work.

Oversized protected histories

Part A is request-sized. If every provider observation plus durable cleanup cannot fit, Refresh refuses before contact and preserves existing claim, review, or books-behind facts. The later M7/F53 persisted engine is the named path that will retire arbitrarily large histories in bounded pages.

Booking identity is later work

Part A identifies provider charges and their rows; it does not add the stable booking-obligation identity the ledger still lacks. Separate orders on one attendee, free package members, and safe pruning of an unreturned sibling remain open. Provider markers are not used to invent that missing relationship.

Historical privacy debt stays visible

Part A does not globally rewrite historical plaintext payment references or old warning notes encrypted only by the database key. New writes use the stronger owner-key boundary; old records remain a named migration limit instead of being silently copied or decrypted in a request.
