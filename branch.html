01 · The change in one screen

Refund state is now a stored fact, not a route’s memory.

The old code could ask a configured provider a yes/no question and then try to infer what to do. The new code carries provider identity, exact Money, explicit failure meanings, a durable generation, local-accounting status, and the human action needed when evidence cannot decide.

Before

Several partial stories

  • The currently selected provider stood in for charge ownership.
  • “Refunded?” collapsed returned amount, pending work, errors, and absence.
  • Single, bulk, refresh, and callback paths could make adjacent decisions.
  • Human-readable notes and attendee rows carried too much safety meaning.
  • A provider success followed by a local failure was hard to resume exactly.
Now

One evidence-led story

  • Every charge admitted to the new refund authority is provider-qualified and blind-indexed.
  • Provider adapters return captured Money, returned Money, events, and typed failures.
  • payment_charges owns the one irreversible refund lifecycle.
  • Short attendee-row claims fence local records while admin work runs.
  • Provider return and local Money recording are separate durable facts.
!

The key design choice: processed_payments does not pretend to be the provider-send authority. It holds a short claim fence and local review/unrecorded work. The globally unique charge in payment_charges owns send generation, replay rules, observation, owner choice, provider completion, and whether local accounting is still due.

02 · The three merge-risk questions

The risky failure modes have named gates and direct proof.

This is the short merge decision. Each concern is answered by a bounded construction in src/ and a regression test that exercises the real failure, not by a comment or an assumed calling convention.

Booking errors

No silent catch-and-continue

An uncertain atomic booking write is reread from primary state. Matching payment and ticket facts recover the booking; a proved rollback creates the protected quantity-zero record and enters the canonical refund path; every ambiguous or contradictory shape rethrows the original error. Placeholder creation also commits its indexed claim and a conservative handled session outcome in the same transaction. If the commit reply is lost, the error still propagates, but a later delivery replays that outcome instead of creating a second attendee or sending money again. The proof is recovery.test.ts, recovery-decision.test.ts, the webhook post-commit recovery suite, and the lost-placeholder- reply regression in index/refunds.test.ts.

Performance

Refund All decrypts at most one attendee

getRefundAllSummary checks the complete listing with no pii_blob. loadRefundAllBatch applies LIMIT 1 before selecting that one encrypted blob, and only then does the route decrypt it. One attendee may expose at most ten indexed references; an eleventh produces a typed refusal before any reference decrypt or provider call. A claim may also encounter rows belonging to other attendees with the same blind reference: that lookup stops at the 101st row and refuses above the 100-row ceiling before decrypting shared state or writing a claim. Both SQL bounds are pinned by integration tests.

Database privacy

New raw references are beyond the DB key

New reference writers create hyb:1 owner-public-key ciphertext and a DB-keyed HMAC for equality. payment_charges also has a storage check that rejects anything outside that envelope. A database plus DB_ENCRYPTION_KEY can see operational metadata, but cannot open these new raw references. Storage, schema, and owner-only detail tests pin the boundary; provider credentials and dormant v1 owner keys remain the explicit caveats below.

✓

Merge reading: the branch materially closes these three risks for its new refund records and refund workflow. It does not claim that all historical payment fields have already migrated, or that possession of provider credentials cannot expose provider-held data.

03 · Canonical authority

Every doorway reaches the same charge-level state machine.

Single Refund, Refund All, Refresh, and paid-callback recovery do not own parallel refund engines. They prepare different evidence, then call the same provider-refund authority. The adapters cannot be called with an ordinary amount or reference; they require the permit minted by this path.

Fact owner

payment_charges

Provider-qualified identity is globally unique. State JSON, plain SQL mirrors, due time, Money, capability, and revision must agree.

Temporary fence

processed_payments

Admin work claims the exact attendee revisions and every indexed representation. It keeps local review or books-behind work, not provider generations.

One permit

AuthorizedRefundRequest

Only the durable engine can mint it; provider adapters require it. This makes bypassing the authority a type and architecture failure.

1

Canonical means there is no runtime bridge beside it. provider-refunds/send.ts owns the only arm/send/replay path and the only production import that can mint a provider refund permit. Two repository modules form the one payment_charges writer boundary: one creates/binds identity, and one owns every Money/state transition. The architecture test rejects a third writer. The old refund-local sender, discovery fallback, read-through admission helper, and live provider_refunded_at reader are absent; the same test fails if any returns. Every refund-facing adapter load passes the complete TaggedPaymentReference through loadRefundProvider, which loads only the tagged provider and verifies the match. The same gate rejects current/last-provider selectors, provider-state lookup, credential enumeration, raw provider loading, and direct adapter imports in refund-facing code. The temporary checkout-session selector is not a refund fallback: an exact allowlist confines getPaymentProviderForExistingPayments to classify.ts, webhooks.ts, and its declaration in payments.ts. It cannot enter admin refunds, the shared engine, or a provider adapter.

04 · Real workflows

Four entrances; one safe middle.

Owner sends a single refund

Load exact person

Owner-only route decrypts that attendee, loads every usable indexed charge, and refuses an incomplete or over-large set.

Price and claim

The route proves the complete operation fits, then transactionally fences attendee revisions and all matching rows.

Read the charge

The provider tagged on the stored reference—and no provider selected from current settings—returns captured and returned Money or one explicit missing/unavailable/invalid answer.

Authorize and act

The charge authority decides whether to send, observe, reuse an answer, or require the owner.

Post and settle

Returned Money is posted by exact reference. Charge-local and attendee-local work retire only after their own proof.

Owner chooses Refund All

Whole set

PII-free safety summary first

SQL counts the complete refundable listing set and detects old unindexed history, review, books-behind Money, or live provider work before a person is opened.

One page

One attendee per submission

The current Bunny request budget proves one attendee’s complete set, so the page loads and decrypts exactly one candidate. Another submission takes the next.

Same engine

No bulk shortcut

The selected person goes through the same exact reference load, claim, provider authority, ledger, and settlement path as Single Refund.

Manager chooses Refresh

↻

Refresh is observation and repair, not permission to send. It takes the same exact row claim, reads the named providers, observes returned or pending work, posts known returns, and retires clean review facts. Its target mode cannot mint a new provider send. Fresh full proof may retire an ordinary owner ambiguity. Fresh partial, backward, or otherwise inconclusive Money instead moves that ambiguity to needs_provider_check, raises the stored returned-money floor when justified, and advances the revision so an older “not sent” form cannot be used. A manager supplies no judgment and cannot send again.

Buyer callback needs an automatic refund

Evidence already names the charge

The validated callback carries its provider, captured Money, session, and provider-qualified payment reference. Callback replay is bound to the same charge authority before any send.

Placeholder stays fenced until fully recorded

When booking cannot be fulfilled, the attendee, zero-quantity booking, owner-key reference anchor, and an exact row claim are written atomically. The exact claimed anchor returned by that insert is carried through provider refund, Money ledger, charge-authority retirement, activity, and note writes; it is never regenerated from the attendee ID. Only its matching settlement releases it after every step succeeds, so any earlier failure leaves a protected repair target.

05 · Evidence vocabulary

The code keeps answers apart until they really mean the same thing.

Captured MoneyMinor units plus three-letter currency, validated at the provider boundary.
+
Refund observationsCompleted, pending, or failed events plus an authoritative cumulative returned total.

Ready

Captured Money is valid, nothing is pending, and no returned amount or contradiction blocks a send.

Already returned

Returned Money exactly equals captured Money. No second send is attempted.

In flight

A supported pending refund is visible. The engine observes; it does not stack another request beside it.

Conflict

Partial return, over-return, several pending refunds, or changed captured Money becomes a typed provider check. It cannot be squeezed into a false owner answer.

Provider reads are total

Answer Meaning May send? What survives
found Validated charge evidence with exact Money. Only if the common judge says ready. The observed evidence and durable authority revision.
missing The named provider explicitly says this charge is absent. No. A ready durable case opens provider_unreadable owner choice immediately; there is no provider guessing.
unavailable Timeout, rate limit, connection, or provider failure. No. A ready durable refund gets a five-minute grace for another observation. If evidence is still unavailable when that finite grace ends, it becomes a required provider_unreadable owner choice—never a silent permanent wait.
invalid Malformed or contradictory successful response. No. A ready durable case opens owner choice immediately. Malformed success never becomes permission to send.

Provider sends are also total

completed, accepted, rejected, not_sent, and uncertain do not collapse into a boolean. A conclusive not_sent can return the same generation to ready. Any possibility that money crossed the network stays armed/observing or goes to an owner choice.

06 · Races, crashes, and retries

The database is the referee.

completed / recordedProvider and local Money agree.
?

Two exits, never one vague “review” state: needs_owner_choice is schema-valid only when at least one real decision is possible. Ordinary uncertainty offers returned or not sent; exact zero-return conflict offers only not sent; exact full-return conflict offers only returned. Partial or inconclusive evidence has no honest money answer, so it is stored separately as needs_provider_check and offers only “Check again.” Neither state has a generic clear. Local Money recording remains a separate action, and every amount uses the charge’s stored currency.

Revision compare-and-swap

Every charge transition names the exact prior revision. A losing writer rereads the winner; it cannot overwrite newer evidence. Replaying identical provider evidence does not manufacture a new revision, while materially changed evidence always does.

Fresh partial evidence closes stale choices

If “possibly sent” was already shown and a later read proves a partial return, the engine replaces that ordinary ambiguity with provider-check work, preserves the returned amount, and advances the revision. The old “not sent” form then loses its revision fence before it can authorize another generation. A conclusive provider-conflict owner choice is not overwritten by later reads. POST also rederives the exact choices from that stored revision; a crafted but otherwise valid answer cannot enter the transaction.

Exact admin claim

The claim transaction checks attendee PII revisions, complete reference rows, sharing rows, blank indexes, and the same command identity. Shared-holder discovery reads at most 101 rows: 100 is accepted, while the sentinel row returns a typed refusal before shared state decryption or any claim write. Blank indexes never share an identity, a set with no usable index skips the sharing query, and either PII revision drift or a disappeared payment row returns changed.

Provider capability matters

Stripe can replay the identical keyed generation for one day. Square's keyed window ends when the command is armed, so it cannot replay later. SumUp is keyless and never auto-replays an armed command.

Arm before I/O

The engine stores that money may move before the provider call. A crash cannot turn “possibly sent” into “safe to try again.”

Admin settlement is always attempted

Every admin refund exit attempts to settle its short-lived row claim. Before a failed ledger post is rethrown, provider-confirmed returns are marked for durable unrecorded work and unproved rows remain in doubt; settlement then tries to persist that answer. Fully-returned provider observations enter those findings before the fallible authority write, so a database error cannot erase evidence that money is back. If the settlement write itself fails, it is reported and the claim may remain; a successful work path throws that settlement error, while a failed work path keeps its original error. The automatic-placeholder claim intentionally follows the stricter all-effects rule described above.

Destructive writes ask first

Delete, merge, finalize, prune, and orphan cleanup read the same lifecycle rules. Delete refuses live work that would lose its repair target; merge may relocate stable indexed work but never an active claim.

×

Old unqualified records do not enter this state machine. Live authority requires a provider-tagged identity. A raw old reference, a DB-key ciphertext, or a reference-bearing processed row with no blind index is a typed refusal before provider I/O. The system does not search every configured provider and does not infer ownership from today’s setting.

07 · Privacy and direct-database reality

New raw identifiers are owner-key protected—but the boundary has named limits.

New references

Owner-public-key ciphertext

New provider references use hyb:1 owner-key encryption. Equality uses a DB-keyed HMAC. SQL sees provider, Money, state, dates, counts, and blind identities—not the raw reference. “Owner-key protected” describes storage; access is still governed separately by each route’s role check.

No broad decrypt

Indexes answer population questions

Refund All summarizes without PII and decrypts one selected attendee. Protected orphan work pages twenty IDs. Provider recovery summaries do not decrypt references; only the owner-only detail does.

Metadata

Finite, not secret, state

failure_data, system notes, lifecycle mirrors, provider name, Money, and due times may be readable with the environment key or directly in SQL. They must never contain buyer PII or raw provider bodies.

1

Direct-DB caveat: provider credentials are environment-key encrypted settings. Someone who has both the database and DB_ENCRYPTION_KEY may decrypt those credentials and use them to query the payment provider. Owner-key encryption protects new identifiers stored in this database; it is not a claim that the provider’s own data is unreachable with stolen credentials.

2

Direct-DB caveat: dormant v1 owner keys remain an older system-wide limit. Modern password-wrapped owner keys keep attendee PII and new payment references beyond a database-plus-environment-key holder. Older v1 wrapped owner-key rows do not provide the same separation until their existing upgrade ceremony runs.

3

Historical data is not silently “fixed” by a request. Old plaintext, DB-key-encrypted, unindexed, or provider-untagged references can still exist. Live refund admission fails closed on them, and ordinary attendee save or merge does not turn an unqualified ID into a live payment row. No admin click scans, decrypts, rewrites, or deletes a whole population. Only the future bounded, owner-authenticated and owner-authorized M11 migration may qualify them; it must verify each canonical write before redacting its source.

Acknowledgement is not a clear

Owner acknowledgement timestamps the exact review revision seen. It does not send, decide provider outcome, erase Money debt, or make a contradiction safe.

09 · Performance and edge limits

The complete operation is priced before it starts.

1 person

Refund All page

One attendee’s complete charge set is the largest current end-to-end command proved to fit the Bunny edge allowance.

10 refs

Per-attendee ceiling

An eleventh indexed reference returns too_many_references before reference decryption or provider I/O.

100 holders

Shared-reference ceiling

Claim SQL asks for at most 101 other rows carrying the same blind reference. The sentinel distinguishes “exactly 100” from “too many”; overflow refuses before decrypting their protected state or writing any claim.

5 calls

Provider concurrency

Independent provider work overlaps in bounded waves; it never creates an unbounded fan-out.

20 IDs

Recovery page

Protected orphan and provider-work queues use keyset pagination and one lookahead rather than broad rows or offsets.

Worst-case, not happy-path, budgeting

Budgets include physical database retries, exact provider attempts, judgment and recovery reads, claim admission, rollback, returned-Money writes, ledger work, settlement, and route tails. Every active reference is priced from its stored provider tag, even when that provider is not currently configured. If the selected command does not fit, nothing narrows itself after a first send.

Critical work gets the allowance

Logging, activity, notification, and Sentry fan-out are deferred until the money-critical scope finishes. The deferred queue also flushes on an error, without consuming the reserve needed to settle or roll back.

One bounded ledger snapshot

Refund planning loads accounts and reference groups in batches, then posts clean plans together. The declared batch path stays at four database round trips even for thirty returned attendees.

Partial indexes make work findable

SQL starts at small live-work indexes for attendee rows and charge authority. Schema restore now understands index predicates so fresh, upgraded, and restored databases build the same paths.

10 · Provider and checkout boundaries

One contract, three honest provider differences.

Stripe Square SumUp
Refund capability Keyed Keyed Keyless
Charge evidence Captured amount/currency, cumulative returned amount, refund objects and states. Captured payment Money plus parsed refund/order resources and states. Transaction Money plus typed refund events; absence is interpreted only where the wire contract permits it.
Retry rule Same generation for up to one day. Replay window ends at arm time; no later automatic replay. An armed generation never auto-replays.
Malformed success Invalid evidence; never “not refunded,” never permission to send.
Transport retries One attempt inside a command. Durable state and a later fresh read own recovery.

Checkout failures stay honest

Known provider absence or buyer-correctable input can become an ordinary refusal. Network, malformed successful response, database, and application errors remain errors; unknown exceptions keep their identity.

Admitted refund facts keep provider identity

Once callback validation has produced a provider-tagged charge, the refund engine keeps that provider and never re-resolves today’s setting. Initial checkout and callback provider selection remain part of the later whole-checkout cutover.

Square recognises its old app orders

Square’s _origin field is a durable “created by this app” marker, not a value that must equal today’s domain. After a domain change, a damaged old app order is still treated as malformed-and-retryable instead of being misclassified as somebody else’s order and terminally acknowledged.

Square monolith is only a structural split

The old large file is separated into client, transport, checkout, connection, order, payment outcomes, read, API, and webhook modules. The distilled report excludes moves and names only changed behavior.

Square payment status is a closed vocabulary

Webhooks accept only APPROVED, PENDING, COMPLETED, CANCELED, or FAILED. Missing, non-text, empty, or unknown status throws at the boundary. Only COMPLETED with an order ID can enter completed-payment handling.

13 · Deliberate limits

What this branch does not claim.

Old data

No live compatibility reader

Pre-index, plaintext, or provider-untagged references do not regain refunds here. Ordinary save and merge do not materialize them. Historical references wait for the bounded, owner-authenticated and owner-authorized M11 migration.

Bulk intent

No durable “finish the listing” job

Each Refund All submission safely completes at most one attendee. A crash leaves remaining candidates discoverable, but this part does not persist an automatic whole-listing cursor.

Later aggregate

No stable obligation allocator

This is the current-charge refund authority, not the later whole-payment, allocation, decision, effect, or delivery aggregate. In particular, the current ledger cannot safely mark a zero-price member of a paid package refunded when the order key has been overwritten by a later order. M7 must introduce the stable, joinable booking obligation that fixes this without guessing. Those later layers must link to this authority, not build a second engine.

Atomic cutover

Not every legacy payment field is gone

The temporary active-provider selector is confined by an exact architecture allowlist to classify.ts, webhooks.ts, and its declaration in payments.ts; it cannot enter admin refunds, the shared refund engine, or an adapter. Historical columns and terminal edge cases remain around blank paid references or malformed signed completions. Once a provider-tagged refund target is admitted, this branch has one authority. The future M6–M11 cutover must replace and delete getPaymentProviderForExistingPayments and every runtime payment-ownership caller in the same change that switches writers, readers, jobs, completion, delivery, and migration. There must be no dual-run or read-through window. After that cutover, credential enumeration may exist only inside settings and activation recovery. It is never payment ownership and cannot enter refund admission, budgeting, provider loading, observation, sending, or dashboard links. No second observer, sender, fallback, bridge, or old-record branch may survive.

Historical privacy

Old plaintext is not erased

This branch closes new reference writes and live reads; it does not perform the later verified redaction of historical raw references or old environment-key notes.

Credentials

Provider access is a separate boundary

Owner-key storage does not protect provider-side data if a database-plus-environment-key holder can decrypt provider credentials.
