01 · What changed

From two vague booleans to one accountable pipeline.

The old flow mainly asked “is it refunded?” and “did the refund work?”. The new flow keeps the evidence, decision, provider action, and accounting result separate—because each can succeed while another is still unknown.

!

This does not promise that every refund succeeds. It promises something more useful: uncertainty cannot masquerade as failure, success, or a safe retry. If the system cannot prove what happened, it parks the work and preserves why.

Before

Call first, infer afterward

  • Choose one globally configured provider.
  • Reduce provider reads and refund calls to true/false or null.
  • Record accounting only when the whole attendee looked successful.
  • Let refresh, single refund, and bulk refund make similar decisions separately.
  • Rely heavily on provider rejection to reveal an earlier refund.
Now

Observe, claim, decide, then act

  • Resolve the exact provider for every charge.
  • Validate captured money, returned money, currency, statuses, and identities.
  • Claim the exact rows before provider I/O and keep the claim through accounting.
  • Use one admission rule across automatic and admin refund paths.
  • Record exact returned references—even when a sibling charge does not finish.

02 · End-to-end money journey

Nine gates between a click and a completed refund.

The crucial ordering is visible here: all references become ready before any provider send. A single attendee is simply a batch of one, so single and bulk refunds cannot drift apart.

  1. Choose candidates

    Keep real ticket holders with at least one stored charge and work still remaining.

    Output: attendee revision + complete charge list.

  2. Prepare old holders

    Fill missing blind indexes and mint deterministic rows for legacy payment_id values that had no row.

    Output: every charge has a durable place to hold.

  3. Claim the snapshot

    In one transaction, recheck the attendee revision, exact row set, and every other row sharing a charge.

    Changed or already held → stop all.

  4. Read every provider

    Tagged charges go to their named provider. Old untagged charges are tried at all credentialed providers.

    Missing, unavailable, invalid, or ambiguous → send nothing.

  5. Bind identity & retry rule

    While the claim is held, store the proven provider and whether repeats are keyed or keyless.

    Output: stable charge identity + retry capability.

  6. Admit or withhold

    Shared money rules decide: already returned, in flight, owner conflict, or safe to send.

    Only “ready” reaches a refund API.

  7. Send once

    The adapter refunds the exact observed capture. Shared references reuse one in-flight promise.

    Output: completed, accepted, rejected, not sent, or uncertain.

  8. Record exact money

    Mark each returned charge across all holders, then reverse only the ledger groups that charge safely explains.

    Output: recorded / review / unrecorded sets.

  9. Settle each row

    Release rows whose answer is known. Keep claims where money may still move; preserve review and books-behind markers.

    Output: durable truth for the next request.

Whole-run readiness

One bad sibling blocks sends for that attendee. A clean charge cannot move while another charge is part-refunded or unreadable.

Five-request budget

Work is packed by charge-reference count, not just attendee count. A merged attendee with many charges still stays within the same provider budget.

Worst result wins

errored → failed → withheld → pending → refunded. A good reference never hides a bad one beside it.

03 · Shared evidence vocabulary

“No answer” is no longer one state.

The types force every caller to distinguish an authoritative absence, a temporary outage, an answer that contradicts trusted facts, and a validated charge.

foundValidated captured money, cumulative returned money, and refund observations.
missingThe provider authoritatively says the charge does not exist—normally a real 404.
unavailableNetwork, timeout, rate limit, configuration, or provider trouble. A later read may help.
invalidThe provider answered, but the shape, identity, account, status, money, or currency cannot be trusted.

A refund call also keeps its exact meaning

completedMoney is proved back.
acceptedProvider owns work still in progress.
rejectedDefinitely refused; no money moved.
not_sentThe request never left this process.
uncertainIt may have landed; keep the claim.
≠

Accepted is not completed. The provider taking responsibility for a refund is visibly different from the buyer having the money. The UI says “still settling” and tells the operator not to send it again.

05 · Claims, rows, races, and books

The database becomes the referee between requests.

Provider idempotency alone is not enough—especially for SumUp. The branch adds an all-or-none claim around the exact row set and keeps it from before the first provider read until after the ledger result is recorded.

grant

No claim exists. This run may hold the row.

held

A fresh run owns it. Send nothing.

resume

A stale claim belongs to this same attendee set. Re-read all evidence.

foreign

Stale work belongs to another owner/scope. Send nothing.

5m

The lease never falls below five minutes. It is the larger of the reservation cleanup setting and one request-lifetime floor. Turning cleanup down cannot make a still-running worker look dead.

Encrypted detail: failure_data stores the structured row record. Older bare failure JSON is read only at this storage boundary.
Plain mirror: protected_state says only the worst live word—claim, unrecorded, or review—so SQL-only maintenance can protect the row.
Compare-and-swap: every rewrite requires the encrypted slot to still equal the value originally read, preventing a late writer from erasing newer work.
Blind identity: payment_reference_index finds every row holding the same money without exposing the charge reference.

What happens when refund and another writer race?

Refund transaction
  1. verify attendee + exact rows
  2. write claim to every holder
  3. commit
  4. read / send / record under claim
Delete, merge, callback, or finalize
  1. read live work in its own transaction
  2. if claim landed first: refuse or retry
  3. if this write landed first: refund sees the new world
  4. no check-then-write gap

Delete

Stops for claim, review, or unrecorded money because it would destroy the repair target.

Merge

Stops for a claim; review and unrecorded markers can travel with rows because merge relocates them.

Finalize

Cannot add or rewrite a matching charge underneath a claimed snapshot.

Prune / orphan purge

Reads the plain mirror and retains rows or attendees with live payment work.

Owner-only money actions

Single refund, refund-all, refresh handling, and payment-review controls use the same owner gates their target routes enforce.

Review is acknowledgement

The new typed-confirmation action clears a review hold. It explicitly does not contact a provider, move money, or invent an accounting correction.

Refresh shares the fence

Refresh claims and reads exactly like refund but branches to observe-only. Confirmed records, activity, and notes land while the same claim is still held.

07 · Honest Part A boundary

What this branch deliberately parks instead of guessing.

Shared obligations

Several rows can legitimately point at one provider charge. Part A detects and parks that situation; it does not yet allocate one charge authoritatively across people.

Ambiguous legacy providers

Two validating providers, an incomplete search, or no validation receives no automatic provider choice. Repair and re-attestation are later work.

Keyless uncertainty

A stale SumUp claim stays observe-only until fresh evidence settles it. Retaining the row is intentional because it may be the only sign money moved.

Global legacy preparation

The authenticated holder pass currently scans all payment-reference rows and attendee PII to close row-less legacy holes. Bounded keyset preparation is deferred.

Provider evidence depth

Stripe’s charge read uses the cumulative returned total rather than an expanded refund list. Square’s strongest schemas cover the payment/refund money boundary, not every endpoint equally.

Owner review is not repair

“Mark reviewed” retires the marker. It does not decide a ledger allocation, correct missing books, or resolve a shared provider reference permanently.
