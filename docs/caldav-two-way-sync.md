## Current-system value

Operators today can only mirror bookings _out_ through the read-only ICS feed
(`GET /caldav/events.ics` in `src/features/feeds.ts`), which calendar apps poll
on their own slow schedule and which never writes into the operator's real
calendar. This feature makes the operator's own calendar (Nextcloud, Fastmail,
iCloud, Radicale — anything CalDAV) contain every dated listing as a real event
— created, updated, and removed as listings change on the site.

The calendar copy is a **mirror, not a second editor**: the site is the boss.
Anything changed on the mirrored events in the calendar is overwritten — at the
next push when the site changes that listing, and otherwise by the **refresh
sweep**: every wake sets aside a small slice of its budget to re-send the
least-recently-pushed mirrored events, so a calendar-side edit or hand-deletion
is corrected within days even when the site never touches that listing. The
settings copy says so in plain words.

Production receivers of the change:

- `/admin/settings` (owner section) — connect, verify, disconnect.
- `listingsTable` in `src/shared/db/listings/records.ts` and **every other
  listing-creation surface** (the statement-based catalog-transfer import in
  `src/features/admin/catalog-transfer/import-listing.ts` and bulk cloning in
  `src/features/admin/bulk-actions.ts`) — every listing write marks the row for
  push.
- Domain settings (`src/features/admin/settings-domains.ts`) — custom-domain and
  host-domain changes bump every dated listing, because pushed events embed the
  listing link and must repush with working URLs.
- Grouping writes (`persistListingJoins` in the listings/groups admin APIs;
  `writePackageMembersTx` in `src/shared/db/groups/membership.ts`) — child-edge
  and package-membership changes flip whether a listing's public page exists
  without touching the listing row, so they bump the affected listings for
  repush.
- Group-row writes that re-page members without touching a join row: a group
  save that changes `is_package` or `hide_package_listings`
  (`src/features/admin/groups.ts`) bumps every dated member, and the bulk
  deactivate/reactivate statement (`setGroupListingsActive` in
  `src/shared/db/groups.ts` — a direct UPDATE that bypasses
  `listingsTable.update`) bumps `caldav_pending` inside that same UPDATE.
- The listing-defaults save (`handleListingDefaultsPost`) — changing the global
  `hidden`/visibility default flips the effective visibility of every
  `use_defaults` listing at read time without writing a listing row, so it bumps
  every dated listing that inherits the changed default.
- Backup restore (`restoreFromSql` in `src/shared/db/backup.ts`) — a restore
  rewrites listings and settings wholesale, bypassing every per-write transition
  above, so it runs the explicit repair in the commands table.
- The factory-reset route (`deleteStorageAndResetDatabase`) — reset wipes every
  listing, stamp, queue row, and CalDAV setting, so no cleanup can survive it.
  Mirrored events staying in the calendar is the **documented outcome**: the
  reset confirmation copy tells the owner their connected calendar keeps the
  events already mirrored and how to remove them in their calendar app.
- The scheduled maintenance runner (`POST /scheduled`,
  `src/shared/maintenance/registry.ts`) — one new task, `caldav_push`, does all
  external calendar IO.

## Scope

- This system is a CalDAV **client** that writes to one operator-pasted calendar
  collection. We do not implement a CalDAV server. Ordinary event
  synchronization is push-only and never reads calendar contents (no REPORT, no
  pull, no conflict rules); the one reading exception is connect-time
  validation, which reads only the bounded PROPFIND response and — on a
  probe-name conflict — the probe resource itself (see Security).
- Only **dated listings** mirror. Bookings/attendees remain feed-only.
- Connected means mirroring; there is no separate direction or pause setting.
  Stopping is disconnecting.
- No foreground request makes a CalDAV call except the connect-time verification
  (a PROPFIND plus a write probe, below). All mirroring IO happens inside one
  scheduled task, a bounded batch per wake. Steady-state edit volume converges
  in one wake (15 minutes on the default monitor cadence); a large backlog —
  first connect on a site with many dated listings — takes several wakes, and
  the sync status says so.

## Valid states

Site-level connection state (settings-backed):

```typescript
type CalDavConnection =
  | { kind: "disconnected" } // may retain dormant identity state, see below
  | {
    kind: "connected";
    // Verified by a live test at save time; stored in canonical form.
    calendarUrl: string;
    // Minted when this calendar was first chosen; stable event identity.
    uidNamespace: string;
    // Bumped by every connection transition; fences stale workers.
    generation: number;
  };
```

Per-listing sync state, from two columns:

| State          | Facts required                  | Meaning                                                         |
| -------------- | ------------------------------- | --------------------------------------------------------------- |
| `unsynced`     | pending = 0, pushed_at null     | No remote copy expected (never pushed, or listing has no date). |
| `pending_push` | pending > 0                     | Local changes not yet on the calendar.                          |
| `pushed`       | pending = 0, pushed_at non-null | Mirrored; the calendar holds what we last sent.                 |

The pending counter is a **revision**, not a flag: every listing write bumps it,
and every push-side clear is conditional on the value the task read, so a
concurrent edit always survives and repushes.

Every task pass ends by writing a **durable sync status** (a settings key:
timestamp, ok/failed, sanitized bounded error summary, and counts — pushed,
deleted, remaining backlog — plus up to five **stuck items**, each naming the
listing by id and name with its sanitized error code, so the operator sees
_which_ listing needs repair, not just that one exists; a queued deletion
carries the name it was queued with, so even a deleted listing's stuck DELETE is
named truthfully). The write is inside the task's database budget and
generation-guarded; without it a scheduled-request failure would be invisible to
the operator, who only ever sees the settings page. Sanitized means codes and
counts — never raw server responses (listing names are the operator's own site
content). Connect and URL-change reset this status to "not yet synced", and
disconnect clears it, in their own transaction — a fresh connection never wears
the previous destination's success, error, or backlog.

## Retry and replay table

| Question                         | Answer                                                                                                                                                                                                                            |
| -------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Stable identity                  | `listing-{id}@{namespace}` and its derived href.                                                                                                                                                                                  |
| Exact replay returns             | Same-bytes PUT to the same href overwrites in place; DELETE replays 404 or 410 into success.                                                                                                                                      |
| Who retries after interruption   | The next scheduled wake — pending rows and queue rows persist.                                                                                                                                                                    |
| What stops two workers           | The maintenance claim (`claimNextMaintenanceTask`); a worker self-fences its external calls before its lease can lapse; generation guards stop a straggler's writes crossing any settings change — same-URL transitions included. |
| Permanent failures               | A PUT the server always rejects: row stays pending, attempt-stamped to the back of the rotation, named (id + name + code) in sync status.                                                                                         |
| Can one failed item block others | No — per-item isolation; never-attempted work goes first but one in four slots is reserved for the oldest attempted rows, so neither fresh nor failed work starves the other.                                                     |

## Concurrency table

| Operation A                         | Operation B                     | Required result                                                                                                       | Protection                                                                                                                                                                                                                              |
| ----------------------------------- | ------------------------------- | --------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Push PUTs listing content           | Operator edits the same listing | The newer edit is pushed on a later wake, never lost.                                                                 | Pending is a revision counter; every push-side clear runs `WHERE caldav_pending = readValue`, so a bump after the read survives.                                                                                                        |
| Date-removal queues a remote delete | Operator restores the date      | No stale delete; the listing repushes.                                                                                | The queue insert is guarded (`… AND date = ''`), **and** the drain rechecks the listing at execution time, dropping the row if it is dated again. ## Security and privacy

- **Who**: the CalDAV settings section is `owner`-only, and no link to it is
  rendered for other roles. No other role has any CalDAV surface.
- **Secrets**: calendar URL, username, and app password are stored via
  `encryptedUpdate` settings (the Stripe-key pattern). The password field is
  write-only in the UI — never echoed back. Test-connection uses the submitted
  values, not stored ones.
- **Outbound guard**: HTTPS only; redirects never followed; the host must be a
  name, not an IP literal or localhost. The only URLs ever requested are the
  canonical calendar URL and hrefs derived from it — each href appends the
  percent-encoded event identity as exactly one child segment and must keep the
  collection's origin and path prefix, or the call fails loudly. This feature
  never follows a server-provided href, so credentials cannot be steered
  anywhere the operator didn't paste. Every request counts against the task's
  declared external budget.
- **Disclosure**: pushing sends listing name, description, location, and date in
  plaintext to the operator's chosen server. The settings copy says this in
  plain words before the operator connects.
- **Untrusted input that causes work**: to the scheduled task, server responses
  are only ever status codes (PUT, DELETE); no response body is parsed beyond
  bounded error summaries for the sync status. Only two bodies are ever read,
  both at connect time and size-capped: the PROPFIND response, inspected solely
  to confirm the target is a calendar collection, and — only when the probe's
  conditional create finds the name taken — that one resource, inspected solely
  to prove it is our own leftover probe. Neither is stored or echoed. A hostile
  or broken server can only make the connect test or later pushes fail, visibly.

## Shared contract (design)

One new module family, `src/shared/caldav/`, split pure-core/thin-shell:

- `vevent.ts` — pure. Build the push payload from a listing: a **complete
  iCalendar object** — VCALENDAR envelope (VERSION, PRODID) wrapping the one
  VEVENT — using the **listings feed's** field set, never the attendee feed's
  `buildVEvent` (it carries attendee identity and must not be reused here). It
  shares (not duplicates) the ICS escaping/date helpers in
  `src/features/feeds.ts` — one ICS vocabulary. The shared `escapeIcs` is
  hardened in passing to normalize `\r\n` and bare `\r` before escaping: today a
  stored description with Windows line endings leaks a raw carriage return into
  the feed's ICS output, which a CalDAV server may reject as malformed
  (regression test: CRLF input). The build uses the same public-visibility gate
  the `/ticket` page and feed use, so an event never links to a page that would
  404. No parser for the sync path: nothing is read.
- `client.ts` — thin IO. URL canonicalization and the one-child-segment href
  builder with its containment check; `testConnection` (authenticated PROPFIND
  that must prove a calendar collection, then the probe proving write access:
  conditional create PUT, overwrite PUT, DELETE — the fixed probe name embeds
  this site's stored token, an existing resource is fetched and proven ours by
  exact token match before it is ever touched, and later probe steps carry its
  ETag as `If-Match`); `put` and `delete` over `fetch` with basic auth,
  `Content-Type: text/calendar; charset=utf-8`, per-call abort deadlines that
  land before the task deadline's margin, the outbound guards above, and
  subrequest counting.
- `push-plan.ts` — pure. `(pendingRows, queueRows) → PushAction[]` where
  `PushAction` is an exhaustive discriminated union (`put`, `refresh` — the idle
  re-send — `queueDelete`, `deleteRemote`, `dropStaleDelete`, `clearLocal` — the
  vacuous dateless clear — and `skip` with a typed reason). The budget split
  between queues, the reserved retry slots, and the refresh sweep's
  leftover-budget rule all live here too. Every rule in the commands table has
  one home, unit-tested and mutation-tested without IO.
- One entry in `src/shared/maintenance/registry.ts` (`caldav_push`,
  `wakePolicy: "scheduled_only"`), draining the queue then pushing under its
  single claim, with `requestFollowUp` for large batches, generation-guarded
  state writes, and the durable sync status written on every pass.

Storage: three listing columns (`caldav_pending` integer revision, default 1;
`caldav_pushed_at`; `caldav_attempt_at` for the fair rotation), a
`caldav_deletes` queue table (derived href + deleted listing id + the listing
name at deletion time, for the sync status + attempt time), a
`caldav_pushed_ids` ledger (namespace + listing id — the durable pre-PUT
identity marker and destination tombstone), and the settings keys (canonical
calendar URL, username, password, the per-destination namespace map, generation,
probe token — minted and stored before the first probe call — settings revision,
sync status).

## Adversarial review

The PR_WORKFLOW challenge questions, answered:

- **External success, local write fails?** Idempotent by identity: re-PUT
  overwrites our own content; re-DELETE 404s into success.
- **Callback replayed?** No callbacks exist; wakes replay by design and are
  no-ops via the pending/queue guards.
- **Follow-up read fails after success?** No follow-up reads exist.
- **Wrong resource id?** Identities are derived from id + immutable namespace;
  nothing is ever addressed by data a server sent us.
- **Two requests run together?** Concurrency table: claims, revision-guarded
  clears, drain-time rechecks, the settings revision, the generation guard.
- **Stale form/revision?** The pending counter guards listing sync writes; the
  settings revision guards saves; the generation guards a leased worker. Every
  stale write fails its condition and becomes a no-op or fails closed.
- **User reloads after interruption?** Save and disconnect are idempotent; sync
  state is server-side.
- **Same resource on another record?** One calendar per site; derived UIDs are
  unique per listing id.
- **One queued item fails permanently?** Isolated per item, attempt-stamped so
  the least-recently-attempted-first selection rotates it behind fresh work,
  surfaced in the durable sync status, never blocks the batch.
- **What does the operator see in unfinished states?** The settings page reads
  the durable sync status: connection state, last result, sanitized error,
  counts, and remaining backlog.

## Approval

Approved by the owner on PR #2064 to start building, with both open questions
decided pragmatically:

1. **Convergence pacing** — **accepted as-is.** A first connect on a site with
   ~100 dated listings taking a few hours to fully mirror is fine: it is a
   one-time background cost on a bounded per-wake budget, the sync status shows
   the remaining backlog throughout, and steady-state edits still converge in a
   single wake. Spending the subrequest budget harder to shorten it would risk
   the 50-subrequest cap for no steady-state benefit.

   splittable — a half-wired mirror (some receivers bumping pending, others
   silently not) is worse than none — so the whole behavior lands together, as
   the completeness-over-slicing rule in AGENTS.md prefers.
